# Контракт мода для позднего подключения

LegitBuilder запускает код мода в уже работающем Minecraft. Это отличается от установки JAR в `mods` до старта игры: часть классов определена, конструкторы и одноразовые события прошли, а Fabric Loader уже сформировал своё состояние. Мод нужно писать так, чтобы entrypoint мог включить его **сейчас**, а не только во время раннего запуска клиента.

## Входной JAR

Собирайте обычный Fabric JAR для точной версии Minecraft и Java 21. В `fabric.mod.json` укажите реальный `client` entrypoint, список Mixin-конфигов и зависимости. Убедитесь, что сами классы, конфиги, refmap, access widener и данные, которые вы намеренно оставляете записями JAR, вошли в готовый файл. Сборка LegitBuilder читает именно готовый JAR, переданный через `-Jar`; каталог исходников мода ей неизвестен. Поздний вызов entrypoint не добавляет мод задним числом в список контейнеров Fabric Loader, уже сформированный при старте клиента. Отсутствие записи в экране списка модов само по себе не показывает, сработал ли этот entrypoint.

Не объявляйте зависимость только ради компиляции, если в целевом процессе её нет. В частности, методы стороннего Fabric API, Mixin Extras, нативные JNI-методы и custom render API должны существовать в работающем клиенте в совместимой версии. Генератор отмечает методы `native`, но не создаёт за мод реализацию JNI. Для них требуется отдельная совместимая привязка.

## Инициализация

Разделите запуск на три действия: зарегистрировать будущие события, прочитать текущее состояние клиента и создать состояние для уже открытого мира. Последнее действие повторяйте при каждом входе в мир, а относящиеся к миру объекты освобождайте при выходе. Если у мода есть GUI, клавиша, HUD, рендер или фоновый сервис, отметьте в журнале не только регистрацию, но и первое реальное событие каждого пути.

Не привязывайте обязательный старт к конструктору `MinecraftClient`, первому tick, созданию окна, загрузке title screen или другому однократному событию. Инжект после этого события не запустит его задним числом. Не выполняйте тяжёлую игровую инициализацию в `static`-полях и `<clinit>` классов данных: они могут быть затронуты до вызова entrypoint. Для клавиш проверяйте события ввода в текущем клиенте; при повторной инициализации не создавайте дублирующие обработчики. Любое обращение к игровым объектам и GPU выполняйте в правильном потоке. Ресурсный reload и переход между мирами должны обновлять только те части состояния, которые от них зависят.

## Mixin и изменение уже загруженных классов

Один конфиг может встретить и ещё не загруженную, и уже загруженную цель. Для второй используется JVMTI redefine, поэтому структура класса ограничена. Проверяйте готовые байты, а не вид аннотации в исходнике. Новое поле состояния, accessor, bridge, дополнительный метод, смена сигнатуры или иерархии могут сделать redefine невозможным; адаптер обрабатывает отдельные случаи, но не даёт общего обхода этого правила. Подробная схема и порядок проверки находятся в [MIXINS.md](MIXINS.md).

Инжектор `@Inject` в метод, который будет вызван позже, может изменить будущие вызовы. Инжектор в уже прошедшую ветку инициализации не заменяет явный вызов из entrypoint. Не снижайте `require` и не удаляйте обработчик ошибки ради зелёного лога: так JAR может «загрузиться», но мод останется выключенным.

## Данные мода

Mixin JSON и refmap обрабатывает внутренний ресурсный мост загрузчика. Игровые `assets/client/...` мод публикует через собственный resource pack и после поздней регистрации выполняет reload. Просто положить файл в исходный JAR недостаточно, чтобы игра нашла его через `ResourceManager`. Шрифты собственного интерфейса компилируйте в Java-классы с байтами и читайте напрямую. Порядок регистрации пакета, адреса шейдеров и сборка шрифтов описаны в [EMBEDDED_RESOURCES.md](EMBEDDED_RESOURCES.md).

## Приёмка мода

Перед тестом в игре запустите `scripts/test.ps1 -Jar C:\mods\my-client.jar` и `java -jar LegitBuilder.jar --inspect`. В игре проверьте инжект из главного меню и в уже открытом мире, одиночный мир, внешний сервер, выход, повторный вход и reload ресурсов. Сверьте журнал инжектора с журналом payload по PID и времени. Успешный `ManualMain` означает, что bootstrap дошёл до завершения; работоспособность функций подтверждают их собственные события и наблюдаемое поведение.
