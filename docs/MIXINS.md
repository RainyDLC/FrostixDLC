# Mixin в работающей JVM

Mixin в этом проекте решает две разные задачи. Если Minecraft ещё не загрузил целевой класс, действующий Mixin transformer может изменить его при первой загрузке. Если класс уже определён JVM, загрузчик получает его текущие байты, применяет конфиг и пытается заменить определение через JVMTI. Второй путь имеет ограничения JVM и не даёт повторно пройти уже исполненные методы.

## Откуда берутся конфиги и байты

Генератор читает массив `mixins` из `fabric.mod.json` в указанном порядке, затем подбирает сами JSON-файлы внутри входного JAR. Он также обнаруживает дополнительные похожие JSON при сканировании архива; полагаться на такое обнаружение как на основной способ регистрации не следует. В конфиге должны совпадать `package`, имена классов, `client`/`mixins`, путь `refmap` и фактические пути `.class` в JAR. Отсутствующий файл или класс должен быть ошибкой сборки или загрузки, а не поводом уменьшить обязательность инжектора.

При запуске встроенные JSON, refmap и `.class` доступны Mixin service wrapper через JNI-таблицу ресурсов. Wrapper сначала ищет путь в payload, затем обращается к исходному service. Для встроенных классов он корректирует отдельные параметры remap инжекторов; `require` при этом не понижается. Конфиги готовятся в действующем Mixin transformer до прямой обработки уже загруженных целей. Это не отдельный Fabric Loader и не автоматическое восстановление всех ранних фаз запуска.

## Цель ещё не загружена

Если JVM ещё не определила целевой класс, будущая загрузка проходит через обычную цепочку трансформации действующего клиента. Этот путь подходит для Mixins, которые меняют структуру класса, **только если** конфиг подготовлен до первого определения цели и конкретная версия Minecraft/Mixin принимает изменение. Поздний entrypoint всё равно не получит события, прошедшие до его запуска. Проверяйте журнал: класс в файле мода и подготовленный Mixin JSON не доказывают, что целевая ветка уже исполнилась.

## Цель уже загружена

Payload находит загруженную цель без повторной загрузки, захватывает её актуальное определение через JVMTI, передаёт его Mixin transformer, затем `LoadedClassAdapter` сопоставляет результат с исходной структурой. Адаптер умеет переносить часть вспомогательных методов в отдельный companion-класс и переписывать обращения. Это специальная обработка известных форм байткода, а не общее разрешение менять схему любого класса. Итог принимает или отвергает `RedefineClasses`.

Для обязательного Mixin к уже загруженной цели проектируйте изменение как замену тела существующего метода при сохранении имени, дескриптора, полей, методов, интерфейсов, суперкласса и иерархии. В реальном выводе Mixin могут появиться синтетические методы, bridge, accessor или поле состояния — их нужно проверять на готовых байтах. Текущий адаптер не гарантирует устранение новых полей; такое поле может остаться в результате и быть отвергнуто JVM. `@Unique`, `@Accessor`, `@Invoker`, `@Shadow`, `@Redirect`, Mixin Extras и изменение доступа проверяйте отдельно: аннотация сама по себе ничего не говорит о допустимости redefine.

JVMTI меняет исполняемый код будущих вызовов. Оно не запускает заново `<clinit>`, не конструирует повторно объекты, не возвращает уже отправленные события и не вызывает `@Inject` для метода, который был вызван до инжекта и больше не вызывается. Если нужна регистрация обработчиков или создание GUI, запускайте её явной функцией из entrypoint. Место для инжектора выбирайте в методе, который действительно будет вызван после подключения: текущий tick, render или обработка ввода. Затем логируйте первое фактическое срабатывание.

## Состояние без нового поля в Minecraft-классе

Если обработчику нужно состояние на экземпляр цели, храните его в классе мода. Типичная схема — карта с идентичностью объекта или слабые ключи, отдельные записи для мира и очистка при отключении. Выберите тип хранения по жизненному циклу объекта: слабая карта подходит не для всех случаев, особенно если значение удерживает ключ. Для глобального состояния используйте отдельный сервис мода. Не объявляйте `@Unique` поле только ради удобства, пока не доказано, что нужная цель будет определена после подготовки конфига.

## Валидация конкретного Mixin

1. Посмотрите в готовом JAR `fabric.mod.json`, конфиг, refmap и `.class` Mixin. Проверяйте готовую сборку, а не каталог исходников.
2. Установите версию и namespace входного JAR. Название метода в исходном коде и в реально загруженном Minecraft-классе может различаться.
3. Запустите загрузчик и найдите в журнале подготовку конфига, имя цели, размер захваченных и преобразованных байтов, результат адаптера и код `RedefineClasses`.
4. Для уже загруженной цели сравните структуру до/после: поля, методы, дескрипторы, интерфейсы, superclass, атрибуты, которые учитывает JVM. Проверьте каждый обязательный обработчик на последующем событии.
5. Проверьте вход в мир после инжекта, инжект в уже открытом мире, выход, повторный вход и reload ресурсов. Один удачный запуск из главного меню не покрывает остальные состояния.

`scripts/test.ps1` проверяет общую Mixin/JVMTI последовательность на изолированных классах и сравнивает байты встроенных классов с входным JAR. Если конкретный Mixin вашего мода требует новой структуры, исправляйте сам Mixin или его точку подключения. Подмена ошибки на «успешно» оставит часть логики неактивной.
