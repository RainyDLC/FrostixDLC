# Сборка и проверка

Для сборки нужны Windows x64, JDK 21, Python 3.10 или новее, CMake и MSVC C++ Build Tools. Значение `-Jar` всегда указывает на **готовый** Fabric JAR вашего мода. Скрипт не запускает Gradle мода и не выбирает «последний найденный JAR» из папки: сначала соберите мод в его проекте, затем передайте точный путь.

```powershell
.\build.ps1 -Jar C:\mods\my-client.jar -Jdk 'C:\Program Files\Microsoft\jdk-21'
```

По умолчанию используется CMake generator `Visual Studio 18 2026`. Если локальный MSVC другой, задайте `-Generator`; путь к CMake можно передать через `-CMake`. JDK берётся из `-Jdk`, затем из `JAVA_HOME` или из доступного `javac.exe`. Зависимости сборки лежат в `dependencies/compile/` и `injector/lib/`, их SHA-256 закреплены в `dependencies/lock.json`. Эти JAR нужны компилятору и упаковщику; они не устанавливают другую версию Mixin/Fabric в уже работающий Minecraft.

## Результат и промежуточные файлы

`build.ps1` собирает генератор `jar-to-dll`, компилирует runtime-классы, создаёт `build/release/mod_payload.cpp`, компилирует payload DLL, рассчитывает carrier под размер PE-образа payload, записывает SHA-256 в `loader-abi.json` и создаёт `build/release/LegitBuilder.jar`. Копия JAR появляется в корне проекта. `build/` и корневой JAR исключены из Git; репозиторий хранит исходники и закреплённые зависимости, а не результат конкретного мода.

В `build/release/` полезны `resource-index.json`, `mixin-index.json`, `loader-abi.json` и `mod_payload.cpp`. Первый показывает, какие непустые записи входного JAR попали в таблицу байтов; второй помогает проверить Mixin-конфиги, третий связывает payload и carrier хешами. Индекс ресурса не доказывает, что файл виден игровому resource manager. Для ресурсов, скомпилированных в Java-классы, проверяйте наличие самих `.class` в исходном JAR и в сообщениях генератора. Отдельная [схема ресурсов](EMBEDDED_RESOURCES.md) объясняет разницу.

## Проверки

Полная регрессия пересобирает результат из того же входного JAR, компилирует Java-тесты, проверяет встроенные Mixin-классы побайтно, работу адаптера, TLS, native capture/redefine и восстановление JVMTI-таблицы в отдельных JVM:

```powershell
.\scripts\test.ps1 -Jar C:\mods\my-client.jar -Jdk 'C:\Program Files\Microsoft\jdk-21'
```

Если путь к `VsDevCmd.bat` отличается, передайте `-VsDevCmd`. Для проверки готового JAR без доступа к Minecraft:

```powershell
java -jar .\LegitBuilder.jar --inspect
```

`--inspect` проверяет встроенный payload, PE64, TLS, таблицу исключений и экспорт `ManualMain`. После сборки можно дополнительно выполнить `jar tf .\LegitBuilder.jar` и проверить `META-INF/MANIFEST.MF`, `mod-payload.dll`, carrier и `loader-abi.json`. Не заменяйте одну DLL внутри архива отдельно: размер carrier и хеши относятся к конкретной сборке.

## Проверка в клиенте

Откройте `LegitBuilder.jar` при запущенном Minecraft соответствующей версии. Без аргументов он выбирает только один подходящий процесс; при нескольких клиентах используйте `java -jar .\LegitBuilder.jar --pid 12345`, указав PID нужного процесса. Если `.jar` связан с `javaw.exe`, ошибки показываются в окне; журнал автоматического запуска лежит в `%USERPROFILE%\.legitbuilder\logs`. Payload ведёт свои журналы в системной временной папке процесса. [Схема инжекта](INJECTION.md) объясняет, как сопоставить их и на каком шаге искать причину отказа.

Тест в игре нужен для фактической функциональности мода: Mixin может не примениться к конкретной цели, entrypoint может не зарегистрировать события, шрифт может декодироваться, но не рисоваться. Проверяйте главное меню, уже открытый мир, повторный вход, сервер и reload ресурсов. Для каждого обязательного обработчика полезна отдельная строка о первом вызове. Ошибку `RedefineClasses` или отсутствующий ресурс исправляйте в моде и его сборке, а не выключением проверки загрузчика.
